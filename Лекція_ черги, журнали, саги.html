    Три гарантії доставки

    At-most-onceНе більше одного разу. Повідомлення може загубитися, дублів немає.
    At-least-onceЩонайменше один раз. Не губиться, але може прийти двічі.
    Exactly-onceЕфект настає рівно один раз. У мережі досягається лише як at-least-once плюс ідемпотентний споживач.

    Збій споживача:

      Перш ніж перемикати: що буде, якщо ack надсилається до обробки, а споживач падає одразу після нього?

      Порядок

      Гарантується лише в певних межах: одна черга з одним споживачем, одна партиція, один ключ. Два воркери на одній черзі вже можуть обробити повідомлення 2 раніше за 1. Порядок замовляють там, де він потрібен: у межах одного замовлення.

      Черга чи журнал

      Брокер-черга зберігає повідомлення, доки його не підтвердить споживач, і видаляє. Журнал зберігає всі записи впорядковано протягом заданого часу; споживач сам пам'ятає, до якого місця дочитав.

      Із практики. Stripe попереджає в документації до вебхуків: та сама подія може прийти більше одного разу, а порядок подій не гарантовано. Slack виносить у чергу завдань усе, що задовге для вебзапиту: у пікові дні це понад 1,4 млрд завдань.

      Основи

      EmailSendRequested — це команда чи подія?

      Команда, замаскована під подію: видавець очікує конкретної дії від конкретного сервісу. Чесна назва — SendEmail, і місце їй у черзі отримувача.

      Чому не можна просто «увімкнути exactly-once» у брокері?

      Бо підтвердження теж може загубитися: брокер не відрізнить «не обробив» від «обробив, але ack не дійшов» і мусить або повторити, або ні.

      Типи черг

      • Quorum — реплікована черга на Raft; усе, що не можна втратити.
      • Classic — нереплікована, на одному вузлі.

      Три підтвердження

      • Publisher confirm: брокер підтвердив видавцеві, що зберіг повідомлення.

      • Consumer ack: споживач підтвердив обробку; до того повідомлення не видаляється.

      Повідомлення не зникає після прочитання. Кожен споживач сам веде свою позицію, тому той самий журнал можна читати багато разів і з різною швидкістю.

      095–103 хвТеорія

      Чому не 2PC і що таке dual write

      Двофазний коміт

      Координатор питає всіх учасників «готові?», і лише коли всі відповіли «так», наказує зафіксувати.

      • Після prepare учасники тримають блокування, доки не озветься координатор.
      • Доступність транзакції — добуток доступностей усіх учасників.
      • HTTP API чужого сервісу і брокер у XA-транзакцію не входять.

      Усередині однієї системи 2PC працює добре (Google Spanner). Між незалежними сервісами — ні.

      BASE замість ACID

      Між сервісами приймаємо eventual consistency: копії даних зійдуться з часом. Проміжок не ховаємо, а моделюємо явно статусом PENDING. Тому POST /orders повертає 202 Accepted.

      Dual writeСервіс у межах однієї операції пише у дві системи (база й брокер) без спільної транзакції. Збій між двома записами лишає їх у різних станах, і ніхто про це не дізнається.

      Transactional Outbox та Inbox

      Атомарно записати в базу і в брокер не можна. Можна записати в одну базу двічі: дані й намір опублікувати. Публікацію виконує окремий процес, який повторює до успіху.

      Як читати outboxЯк працюєКоли брати
      Polling publisherперіодичний SELECT неопублікованих рядківпросто, без додаткової інфраструктури; наш варіант
      Transaction log tailing (CDC)читання журналу транзакцій бази, наприклад Debezium Outbox Event Routerвисоке навантаження, мінімальна затримка, вже є Kafka Connect
      InboxТаблиця на боці споживача: у тій самій транзакції, що й бізнес-зміна, фіксується ідентифікатор обробленого повідомлення. Повторна доставка нічого не змінює.

      Saga: ланцюжок локальних транзакцій

      SagaПослідовність локальних транзакцій у різних сервісах. Кожна публікує повідомлення, що запускає наступну. Якщо крок не вдався, для вже завершених кроків виконуються компенсуючі транзакції. Термін: Гарсіа-Моліна і Салем, 1987.

      Компенсація — не rollback

      Проміжний стан уже бачили інші, тому «скасувати» означає виконати нову дію: зняти резерв, повернути кошти. Компенсація має бути ідемпотентною і не має права остаточно впасти.

      Ізоляції немає

      З ACID сага зберігає A, C і D, але втрачає I. Захист: semantic lock — проміжні статуси PENDING, CANCELLING, які показують, що над записом працює незавершена сага.

      public class OrderStateMachine : MassTransitStateMachine<OrderState>
{
    public State Pending { get; private set; }
    public State StockReservedState { get; private set; }
    public State Cancelling { get; private set; }

    public Event<OrderSubmitted> Submitted { get; private set; }
    public Event<StockReserved> Reserved { get; private set; }
    public Event<StockRejected> Rejected { get; private set; }
    public Event<PaymentCompleted> Paid { get; private set; }
    public Event<PaymentFailed> PayFailed { get; private set; }
    public Event<StockReleased> Released { get; private set; }

    public OrderStateMachine()
    {
        InstanceState(x => x.CurrentState);
        Event(() => Submitted, e => e.CorrelateById(m => m.Message.OrderId));
        // так само CorrelateById для решти подій

        Initially(When(Submitted)
            .Then(c => c.Saga.Amount = c.Message.Amount)
            .Send(new Uri("queue:inventory.reserve"),
                  c => new ReserveStock(c.Saga.CorrelationId, c.Message.Sku, c.Message.Quantity))
            .TransitionTo(Pending));

        During(Pending,
            When(Reserved)
                .Send(new Uri("queue:payment.charge"),
                      c => new ChargePayment(c.Saga.CorrelationId, c.Saga.Amount))
                .TransitionTo(StockReservedState),
            When(Rejected)
                .Publish(c => new OrderCancelled(c.Saga.CorrelationId, c.Message.Reason))
                .Finalize());

        During(StockReservedState,
            When(Paid).Publish(c => new OrderCompleted(c.Saga.CorrelationId)).Finalize(),
            When(PayFailed)
                .Send(new Uri("queue:inventory.release"),
                      c => new ReleaseStock(c.Saga.CorrelationId))   // компенсація
                .TransitionTo(Cancelling));

        During(Cancelling,
            When(Released)
                .Publish(c => new OrderCancelled(c.Saga.CorrelationId, "payment failed"))
                .Finalize());
    }
}

      Подієво-орієнтована архітектура
      
  
      
  
      «Event-driven» — це чотири різні патерни, які постійно плутають. Два з них ми вже використали в демо, не називаючи.
      
  
      
    
      ПатернСутьДе бачили
      
    
      
      Event notificationподія лише сповіщає; за деталями споживач іде до джерелаStockReserved(orderId)
      
      
      Event-carried state transferподія несе дані, споживач тримає власну копіюOrderCreated із сумою → платіж PENDING у payment
      
      
      Event sourcingстан зберігається як послідовність подійжурнал публікацій The New York Times у Kafka
      
      
      CQRSокремі моделі для запису й для читанняAnalyticsListener: лічильники з потоку подій
      
    
      
  
      
    
      Еволюція схем
      Подія — публічний API без версії в URL, і вона живе в журналі роками. Безпечно лише додавати необов'язкові поля. Споживач ігнорує невідомі поля (tolerant reader). Інструменти: Schema Registry, AsyncAPI, CloudEvents.
      
    
      Спостережуваність
      У кожному повідомленні — correlation id і контекст трасування (traceparent). Три метрики, без яких не виходять у продакшн: довжина черги або consumer lag, розмір DLQ, вік найстарішого неопублікованого рядка outbox.
      
    
      Антипатерни
      • команда, замаскована під подію;
      • подія як відбиток таблиці з усіма колонками;
      • усі підписані на все: розподілений моноліт;
      • довгий ланцюжок хореографії, якого ніхто не може намалювати.

      Контрольні запитання
      
    
      Споживач обробив повідомлення й упав до ack. Що зробить брокер і до чого це приведе?
      Доставить повторно. Без ідемпотентності дія виконається двічі.
      
    
      Назвіть два наслідки dual write залежно від порядку записів.
      База, потім брокер: втрачене повідомлення. Брокер, потім база: повідомлення про те, чого не існує.
      
    
      Яку гарантію дає outbox і чому не exactly-once?
      At-least-once: релей може впасти після публікації, але до позначки «опубліковано», і повторить відправку.
      
    
      Чим компенсуюча транзакція відрізняється від rollback?
      Це нова зафіксована дія. Проміжний стан уже бачили інші, тож «відмотати» його неможливо.
      
    
      У демо оплата йде після резерву. Що зміниться, якщо поміняти їх місцями?
      Компенсацією стане повернення коштів: дорожче, повільніше й помітно клієнтові.
      
    
      Чому в хореографії перехід у COMPLETED дозволено і з PENDING, і зі STOCK_RESERVED?
      Події йдуть різними чергами: payment.completed може випередити stock.reserved.
      
    
      Inbox захищає від повторної доставки. Від чого він не захищає?
      Від двох різних повідомлень про одне й те саме. Тут рятує лише бізнес-ключ з унікальним обмеженням.
      
    
      У сценарії «немає товару» в хореографії платіж лишається PENDING. Як це виправити?
      Payment має підписатися на order.cancelled і закрити платіж. Це ще одна підписка, яку легко забути: типова ціна хореографії.
